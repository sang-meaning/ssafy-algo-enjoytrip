# 성능 측정 결과

측정 환경: Intel Xeon 2.1GHz 2코어, JDK 21, 관광지 48,508건
다시 측정하려면 `test/com/ssafy/enjoytrip/bench` 의 두 클래스를 실행한다.
PC 마다 절대 시간은 다르지만 알고리즘 간 비율은 비슷하게 나온다.

정리

- 완전탐색은 O(n!) 이라 지점이 하나 늘 때마다 약 10배씩 느려진다. 11곳에서 이미 115ms.
- 비트마스크 DP 는 O(n^2 * 2^n). 15곳까지 20ms 이내라 웹 요청 한 번에 충분하다.
  16곳부터는 시간과 메모리가 2배 넘게 늘어나므로 서비스에서는 15곳까지만 DP 를 쓴다 (`AutoTsp.EXACT_LIMIT`).
- 하향식 DP 는 상향식과 갱신 횟수가 같다. 상태 수가 같기 때문에 하향식으로 바꿔도 다룰 수 있는 지점 수는 늘지 않고,
  재귀 호출 비용 때문에 n 이 커질수록 상향식보다 30~60% 느려졌다.
- 최근접 이웃 + 2-opt 는 18곳에서도 0.1ms 이하. 최적해보다 평균 0~6% 길다.
  그래서 16곳 이상은 2-opt 로 근사해를 낸다.
- 8곳에서 상향식이 튀는 것은 JIT 컴파일 시점 차이로 보인다. 반복 측정 시 줄어든다.

## 2. 자동완성 (Trie)

관광지 이름 48,508건. 검색어당 상위 10개. (`SearchBenchmark`)

트라이 구축 305ms, 노드 483,565개, 메모리 약 58.7MB (일반 트라이 + 초성 트라이)

| 검색어 | 트라이 (us) | 전체 순회 (us) | 배수 |
|---|---|---|---|
| 경 | 0.11 | 239.8 | 2153 |
| 경복 | 0.13 | 236.4 | 1772 |
| 경복궁 | 0.12 | 240.0 | 1947 |
| 해운대 | 0.13 | 252.4 | 1883 |
| ㄱㅂㄱ | 0.15 | 325.4 | 2177 |
| ㅎㅇㄷ | 0.16 | 298.8 | 1922 |
| 부산 | 0.16 | 242.3 | 1517 |
| 제주 | 0.12 | 252.2 | 2033 |
| 롯데 | 0.11 | 271.0 | 2449 |
| 국립 | 0.13 | 260.0 | 2069 |

정리

- 트라이 검색은 O(검색어 길이 + K) 로 데이터 수와 무관하다. 전체 순회는 O(N * L).
- 각 노드가 상위 K 개를 미리 들고 있어서 접두어 노드까지 내려가면 바로 결과가 나온다.
  추천 순위가 높은 항목부터 넣으면 노드마다 먼저 들어온 K 개가 곧 상위 K 개라 정렬이 필요 없다.
- 대신 메모리를 약 59MB 쓴다. 자식 노드를 HashMap 대신 정렬된 char 배열로 관리해서 줄인 값이다.
- 키 입력마다 호출되는 기능이라 응답 시간이 중요하고, 공공데이터 API 는 하루 1,000건 제한이 있어
  서버 메모리 트라이로 처리하는 것이 맞다.

## 3. 반경 검색 (격자 공간 인덱스)

무작위 관광지 500곳을 중심으로 반경 5km 검색. (`SearchBenchmark`)

격자 인덱스 구축 95ms, 칸 10,086개 (0.02도, 약 2.2km 간격)

| 반경 5km 검색 (500회 평균) | 시간 (us) | 평균 결과 수 |
|---|---|---|
| 격자 인덱스 | 154.2 | 485.8 |
| 전체 순회 | 4423.8 | 485.8 |

정리

- 원이 걸치는 칸만 보면 되므로 약 29배 빠르다. 결과 개수는 전체 순회와 같다 (정확성 확인).
- 랜덤 경로 후보 찾기, 지도 화면 영역 마커 조회에 같이 쓴다.
